# 证据目录（EVIDENCE）

这个目录收录 LeziBench 的**真实运行证据**：不靠"我们测试过了"这种说法，
而是把命令输出、报告原文、失败轮次一并留档，供任何人复核。

> 全部数据来自 Windows 11 + Node v24.20.0 + DSH 桌面端的真实执行。
> 每题作答由 Agent 逐题读题面完成，**未使用** `scripts/oracle-answers.mjs`。

### 为什么主证据用 98 分

A 局真的答错了一道题，判分器准确指出了错在哪：

```
D03.C1  亏本 SKU 应为 A-101, C-315，实际为 C-315
```

供应商进价 `A-101 = 56`、门店售价 `53`；`C-315` 进价 `21`、售价 `16`。
两件都亏本，答题者只挑出了 `C-315`，漏了 `A-101`，扣 2 分。**没有重跑、没有挑分。**

一个带具体失分点的 98 分，比满分更能证明：

- 判分器**真的在逐条比对**，不是「答了就给分」
- 分数**真的会因为漏看一个条件而下降**
- 报告会**告诉你具体错在哪**，而不只是一个数字

B 局是同版本下另一次作答，满分。**两局放在一起，说明 98 不是「题目太难」，100 也不是「判分放水」** ——
同一份卷子，答得全对就 100，漏一个条件就 98。

### A 局的答案文件也在仓库里

`host/answers-batch1..4.json` + `host/submit-batch1..4.log` 是 A 局逐题写下的答案与 CLI 原始输出。
**任何人都能逐题核对**：这些答案是人读题面写出来的，还是 oracle 吐出来的。

## 七、这些测试的判据说明

红队套件（`evidence/*.test.mjs` + `mutation-check.mjs`）已经被接入 CI
（`.github/workflows/ci.yml` 的 Node 20 job），任何一条变红都会阻断合并。
下面把判据分成两类讲清楚，避免读者误以为"全都要求 0 分"。

### 7.1 绝对判据（不满足就是 bug，没有商量余地）

这些是**确定性**的，与概率、分布、抽样无关：

| 判据 | 在哪 | 为什么是绝对的 |
|---|---|---|
| **正确答案必须满分** | `seeds.test.mjs` | 题目的 `oracle(facts)` 是唯一权威答案；它拿不到满分，说明判分器与题目不自洽 |
| **`awarded` 不得越界** | `equivalence.test.mjs` | `0 ≤ awarded ≤ maxPoints`，任何越界都说明权重计算错误 |
| **`generate()` 不得抛异常** | `seeds.test.mjs` | 出题器崩溃 = 整套系统不可用（曾真实发生过一次） |
| **空答案 → `MISSING_ANSWER`** | `equivalence.test.mjs` | 空白不是"知识错误"，必须与"答错"区分开 |
| **乱码 → `UNPARSEABLE`** | `equivalence.test.mjs` | 解析失败不能被静默当成 0 分知识错误 |
| **示例里不得出现真实答案值** | `antileak.test.mjs` | 只比对"示例行是否含真实 position 数字 / 完整答案 JSON"，是字符串级的确定性检查 |
| **同一 seed 两次判分完全一致** | `seeds.test.mjs` | 判分必须是纯函数，不得有隐藏状态 |
| **同 seed 两次 `generate()` 题面一致** | `seeds.test.mjs` | 确定性出题是"可复现成绩"的前提 |
| **公开实例不得泄漏 `facts` / `oracle`** | `seeds.test.mjs` | `instantiate()` 只应返回题面，不能把内部数据带出去 |
| **变异必须被检出** | `mutation-check.mjs` | 把判分器强制改成恒真/恒假，对应对抗/等价断言必须变红 |

### 7.2 统计学判据（有阈值，因为题目本身有结构下限）

这些判据**不能要求 0**，因为被测对象本身带随机性或选择题下限。
写死"必须 0"只会得到两种结果：要么测试永远红，要么为了变绿而把断言改成空转
（`assert.ok(true)` 那种）——后者比没有测试更危险。

| 判据 | 阈值 | 统计学理由 |
|---|---|---|
| **R04「姓名序 == 位置序」** | ≤ **15%** | 位置是 1–4 的随机排列，共 4! = 24 种等可能结果。「姓名顺序恰好等于位置顺序」占其中 1 种，故**即使实现完全正确**也有 1/24 ≈ 4.2% 必然命中。实测 1500 seed 为 5.67% ± 0.60%（95% 上界 6.8%）。阈值取 15% ≈ 2.5 倍上界：若实现退化为"位置恒等于姓名序"（泄漏），命中率会是 100%，远超 15%；同时 n=60 时抽样标准误约 ±3%，15% 留足余量不会 flake。（旧的 12% 实测中出现过 11.7%，属阈值过紧） |
| **D02 固定模板命中率** | ≤ **45%** | D02 是 A/B/C 三选一。"固定答 C + 通用理由"在**正确答案确实是 C** 的 seed 上本来就该满分，这不是缺陷。三选一的结构下限约 33%；阈值 45% 允许合理波动，又能抓住"答案分布又偏了"（历史上曾偏到 68%，那时固定模板能拿满 100%）。 |
| **照抄示例的平均得分** | ≤ **0.5 分** | 多数题的示例已是 `<...>` 占位符（非法 JSON），结构上无法照抄，天然为 0。少数题（D01/C02）示例仍是具体值，个别 seed 下可能恰好与某个 criterion 重合。要求"每个 seed 都 0 分"既不现实也不必要；按题平均 ≤0.5 分既能容忍低概率巧合，又能抓住"示例含真实答案成分"的系统性泄漏。 |
| **单题固定答案基线** | ≤ **满分 40%** | 取 seed=0 的整套答案，在 60 个 seed 上回放。40% 是"明显高于瞎猜、但还没到整题可背"的分界线。 |
| **跨题固定答案基线** | ≤ **25/100** | 16 题合计的背答案上限。当前实测 18.2/100，其中约 9 分来自单选题的数学下限（status 二选一、D02 三选一、C03 四组合、C04 rootCause 恒定），不是实现缺陷。 |
| **D03 只填两个常量字段** | ≤ **2/6** | D03 的三个字段里有两个曾在所有 seed 下恒定（`onlyInStore`、`commonCount`），导致不读题就能拿 2/3。阈值 2 分对应"最多只拿到一个字段"。 |
| **至少 90% 的题面随 seed 变化** | ≥ **90%** | 允许极少数题（规则完全写死）有较少变体，但不能大面积退化。 |
| **答案不得跨 seed 完全恒定** | 整份答案 0 题恒定 | 某题整份答案恒定 = 背一个字符串通杀。若确属设计使然（如 C04 的 rootCause），必须显式登记在 `DESIGN_CONSTANT` 白名单并写明理由，而不是悄悄放宽阈值。 |

### 7.3 我们不追求什么

**不追求"固定答案拿 0 分"这种不现实的目标。**

三选一题必然有 33% 的瞎猜基线；二选一必然有 50%。
如果红队测试写成"固定答案必须 0 分"，那么唯一的通过方式是让每道题都变成
"答案空间无限大"——那会把可解释、可逐条复核的判分器变成模糊打分，得不偿失。

**真正要防的是这两件事**：

1. **答案跨 seed 恒定** —— 考生背一次就能通杀所有局。这是**设计缺陷**，
   不是难度问题；判据是"整份答案不得恒定"，而不是"每个字段都不得恒定"
   （C04 的 rootCause 恒定是合理的，因为它只占 3/9，且 C2/C3 必须真算）。
2. **示例泄漏真值** —— 题面里的示例 JSON 恰好就是标准答案。这是**送分**，
   判据是"示例里不得出现真实值"（确定性）+ "照抄平均 ≤0.5 分"（统计兜底）。

### 7.4 断言自身的健康度

红队测试最危险的失败模式不是"红"，而是**假绿**：断言写得看起来在测，
实际因为 `if (...) return`、`n=0` 时 `NaN > 0 === false`、或者
`assert.ok(x >= 0)` 这类恒真条件而从不执行。

本套件对此做了三件事：

1. **变异检出**（`mutation-check.mjs`）：把 `grade()` 强制改成恒真/恒假、
   把正确字段改错、把输入换乱码，共 64 个变异点。
   **要求 64/64 全部被检出**——任何一个没被检出，说明对应断言是空的。
2. **覆盖数守卫**：凡是"遍历 seed 但可能 `continue`"的用例，都额外断言
   「至少 N 道题真的被检查到」（如 `report.length >= 3`、`covered.length >= 3`），
   防止占位符化后用例悄悄退化成空转。
3. **主动扫 seed**：不再依赖"基准 seed 恰好落在某个分支"。
   例如 D02 的"比较句不应误杀"用例，会主动扫 200 个 seed 找到答案为 C 的实例
   来断言；扫不到则用例自身失败（说明该分支已不可达）。

> 以上三条的实践证据：审查期间确实抓到过 2 个假绿用例
> （`assert.ok(sampleable >= 0)` 恒真、`if (o.answer !== 'C') return` 在
> SEED=42 下从不执行），已修复并用注入泄漏的方式验证过它们现在会红。

### 7.5 在 CI 里的位置

```yaml
# .github/workflows/ci.yml（只在 Node 20 那个 job 跑，避免三倍耗时）
- name: 红队套件（evidence/）
  if: matrix.node == '20'
  shell: bash
  run: |
    node --test --test-timeout=300000 evidence/*.test.mjs
    node evidence/mutation-check.mjs
```

用 glob 而不是逐个列文件，将来 `evidence/` 下新增 `*.test.mjs` 不必改 workflow。
`--test-timeout=300000` 必须保留：这几个套件合计要跑 3–5 分钟，默认超时会把
"跑得慢"误判成"测试失败"。
