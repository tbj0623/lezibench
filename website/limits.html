这份工具测不了什么

一个评测最该说清楚的不是它能测什么，而是它测不了什么。 下面每一条都是这套设计的直接后果，不是「以后会改进」的客套话 —— 有些是权衡，有些是永久边界。

题库是公开的，可以被读

16 道题的题面生成逻辑、评分条件、判分器、甚至标准答案的推导方式，全都在 src/ 目录里， 用任何一个文本编辑器就能读。

这不是疏忽，是有意的选择。理由很直接：一个不能看的评测，你没法判断它到底在测什么， 也没法在你觉得判错的时候去核对。闭源评测的「权威感」来自不透明，而不是来自正确。

但代价必须说清楚：

  • 模型如果读过这个仓库，可能对某些题面有「记忆优势」，分数会偏高。
  • 任何人都可以改题、改判分器、改答案文件；改了当然能拿高分，但那份分数只对改的人有意义。
  • 所以这里没有「防作弊」这个概念。我们不做，也不宣称做。

换句话说：LeziBench 的分数可信度，建立在「你没改它」这个前提上。 这是一个自测工具的合理前提，但不是一个认证机构能接受的前提。

不是认证，不防作弊

每一份报告自己就印着 本地规则核验 · 非认证成绩（LOCAL_SELF_TEST）。具体地说：

  • 没有第三方见证。判分发生在你自己的机器上，没有可信第三方能证明这份成绩是真跑出来的。
  • 没有身份核验。没有登录、没有账号、没有签名。谁都能跑，也谁都能声称某个分数是自己的。
  • 没有被测对象锁定。报告不记录「是谁在答题」，也不验证答案是否由被测模型产生。
  • 没有排行榜。没有中心服务器就没有共同基准，做了排行榜也只是一个可以被随意提交的列表。

如果你需要的是「可用于对外宣称的能力认证」，这个工具解决不了你的问题 —— 它给出的是一份可以自己核对的能力体检报告。

16 题覆盖不到的东西

四个维度、十六道题，覆盖面是刻意收窄的：只测「给定材料、给定规则、要求产出结构化答案」 这一类任务。下面这些它完全测不出来：

测不到的能力维度
能力为什么测不到
长上下文 单题材料最长不过两三百字。真实场景里「两万字文档里找一处矛盾」这类能力，这里没有对应题目。
多轮工具调用 整套题是「一次作答、一次判分」，没有需要连续调用工具、根据返回值调整策略的任务。
代码工程能力 没有需要读仓库、改代码、跑测试的题。C04 只是看一段十行的伪代码，不是工程任务。
开放式写作与审美 判分是确定性代码，只能判「可形式化的对错」。文风、结构、说服力没有判据。
事实准确性 / 幻觉率 题目自带全部事实，不需要模型调用外部知识。所以它不测「知不知道」，只测「给了材料用得对不对」。
安全性与拒答 没有对抗性输入、没有越狱尝试、没有需要拒绝的请求。
多语言能力 题库全部为中文。非中文能力不在覆盖范围内。
推理深度上限 最难的一题是四元素排列约束求解，规模很小。它不区分「能做」和「能做得很深」。

还有一个更隐蔽的边界

因为题目是模板化生成的（同一道题每次只换数字和名字）， 所以它测的是「在同一类任务上稳不稳定」，而不是「面对陌生任务时能不能迁移」。 一个模型可能把 16 种题型都练熟，但在没见过的任务形态上完全失灵 —— 这份试卷看不出来。

什么样的比较没有意义

下面这些比较，做了也是白做，甚至会得出错误结论：

跨版本比较 ✗

只有 examVersion 与 graderVersion 都相同的两次运行才能比。 版本不同意味着题目或判分口径变了，分数不可比。报告里两个版本号都印着，对一下就知道。

不同温度 / top_p / 采样参数之间比较 ✗

同一模型在 temperature=0 和 temperature=1 下是两种不同的行为模式。 前者稳定但可能错过需要探索的路径，后者方差大。把两次运行的分差直接归因于「模型能力」是错的。 要比较就先固定采样参数，并且各跑多次取分布，而不是比单次结果。

不同工具配置 / 系统提示之间比较 ✗

有没有联网、有没有代码执行、系统提示怎么写、上下文里塞了什么，都会影响结果。 一个开了工具的 Agent 和一个裸模型跑同一套题，分数不可直接比 —— 这不是同一种被测对象。

单次运行之间比较 ✗

每局题目由 seed 生成，题面数据不同。单次运行的分数有随机性， 一两分的差距完全可能在噪声范围内。要比就多跑几局看分布，而不是比一次。

和别的评测的分数换算 ✗

LeziBench 的 80 分和任何其他评测的 80 分没有对应关系。满分 100 不代表它是百分比， 也不代表它和某个「通过线」挂钩。

耗时不是能力指标

报告里有一项「实测耗时」，它是从 start 到最后一批评分完成之间的墙上时钟时间。 这个数字受以下因素影响，且这些因素都不是被测模型的能力：

  • 宿主机性能、当前负载、磁盘速度；
  • 模型 API 的网络往返与排队；
  • Agent 框架本身的开销、重试策略、上下文长度；
  • 作答时是否先去查了资料、跑了工具。

所以：不要用耗时给模型排名，也不要把耗时和分数拼成一个「性价比」指标。 这个字段的用途只有一个 —— 让你知道这次跑了多久。

确定性判分的代价

选择用代码判分而不是用模型判分，换来的是可复现和可审计，代价是判分只能覆盖可形式化的部分。

  • 格式不对可能被判成「待复核」，而不是「错」。 如果答案里有内容但一个字段都识别不出来，这道题会进入 UNPARSEABLE，整局降级为 PARTIAL。 这比误判成 0 分更诚实，但也意味着「格式规范」本身成了一道隐性门槛。
  • 同义表述覆盖不全。别名表是显式列举的，没列进去的等价说法不会被认。 这是「不猜」的代价：宁可判待复核，也不猜你的意思。
  • 题目必须能被形式化。凡是没法写成「通过 / 不通过」的任务，都进不了这个题库。 这直接导致了上面「测不了什么」那一整张表。

V1 版本的具体边界

当前版本 0.1.0（exam v1.0.0 / grader v1.0.0），已知的具体限制：

  • 只有 standard 一种模式。传入其他模式会明确报错，不会静默降级。
  • 客户端可改。state.json、答案文件、判分器都在本地，没有签名校验。
  • 只有中文。题库、理由、报告都是中文。
  • 只有 16 题。没有题库轮换，跑第三次开始就会有熟悉度。
  • 已判分的批次不可覆盖。答案写错了只能新开一局，不能就地重答。
  • 无并发保护。两个进程同时对同一 runId 提交，行为未定义（原子写保证文件不损坏，但不保证逻辑顺序）。
  • 平台验证不完整。只有 DSH 与 Windows 真机跑通过；macOS / Linux 有实现但未跑完整局； OpenClaw / Codex 完全未核实。详见支持环境表。

最后一句

如果你要用这份成绩对外说点什么，请至少带上三件事： 总分、exam / grader 版本、以及「本地自测，非认证」这句话。 少了任何一项，这份成绩就变成了它本来不是的东西。
