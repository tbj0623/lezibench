它到底会不会联网

跑分过程需要联网吗？

不需要。判分、写状态、生成报告全部走本地文件系统。代码里没有任何 HTTP 客户端， 也没有 API key 的概念 —— 不是「默认不联网」，是根本没有联网的代码路径。

验证方法：断网后跑 doctor，五项仍然全 ✔；再跑完整一局，报告照样生成。

我的答案会被上传到哪里吗？

不会。答案写到本机数据目录下的 runs/<runId>/answers/， 报告写在同目录的 reports/。除此之外没有第二个副本。

具体路径见隐私说明。

为什么不需要 API key？

因为判分不调用任何模型。LeziBench 的判分器是一段确定性 JavaScript 代码， 它对照题目的 publicCriteria 逐条判定。没有模型参与，自然不需要凭据。

这也是它能在断网环境里出分的原因。

网站本身有追踪吗？

没有。这个站点是纯静态页面：没有 Cookie、没有分析脚本、没有外部字体、没有 CDN。 唯一的浏览器存储是一个 localStorage 键，用来记住你选的明暗主题。 关掉 Cookie 或不选主题，功能完全不受影响。

它测的到底是什么

它测的是「聪明程度」吗？

不是。它测的是「在给定材料、给定规则、要求输出结构化答案」这一类任务上， 这一次做得怎么样。四个维度分别是：

  • 指令理解：多条通知里哪条最终有效、规则有例外时怎么处理。
  • 逻辑推理：算账、排顺序、满足多个约束的最优解、排除法求解。
  • 信息整理：去重排序、区分事实与推断、两表合并且找冲突、按规则分类。
  • 状态追踪与纠错：改来改去之后的最新状态、发现算式错误、新旧规则更迭、定位 bug 根因。

完整的边界见测不到什么。

为什么只有 16 题？会不会太少？

16 题确实不多，这是一个明确的权衡：题少才能保证每一题都被认真设计成「有区分度」， 且每一条评分条件都能被人工复核。

但也正因为题少，单次运行的方差不可忽略。要看水平就多跑几局看分布， 而不是盯一次分数。

为什么分 4 批，不能一次把 16 题都给我吗？

可以，但当前版本不提供。分批是刻意的：一次只看 4 道题，注意力会集中在「把条件读清楚」， 而不是「扫一遍挑容易的做」。这也是真实任务的形态 —— 你不会一次拿到 16 个任务再统一交卷。

另外，分批也让「提交幂等」「断点续跑」这两件事变得简单可靠： 每一批是一个原子单元。

题目每次都不一样吗？

题目的结构固定（16 道、4 批、分值不变），但数据由 seed 生成： 日期、金额、人名、商品编号、名单都不同。所以同一道题连跑两次，看到的题面是不一样的。

传 --seed <值> 可以复现同一套题面 —— 排查问题或者对比时有用。

关于分数与比较

80 分算好吗？

段位表是这样切的：90+ 卓越、80–89 优秀、65–79 良好、50–64 基础、0–49 需要提升。 所以 80 分落在「优秀」。

但比段位更有用的是看哪几条条件没过。一个 80 分里有 20 分是怎么丢的， 比「80 分算不算好」这个问题重要得多。

我能拿这个分数跟别人的比吗？

只有在下面条件全部满足时才有意义：

  • 两次运行的 examVersion 相同；
  • graderVersion 相同；
  • 采样参数（temperature 等）相同；
  • 工具配置与系统提示相同；
  • 各自跑了多局，比的是分布而不是单次结果。

少任何一条，这个比较就不成立。展开见什么样的比较没有意义。

为什么同一份答案重判，分数可能变？

正常情况下不会变 —— 判分是确定性的。分数变化只有一种合法来源： grader 版本升级了，判分口径变了。

regrade 会把重判前后的分数差异逐题列出来，并把旧轨迹归档到 evidence/。 它不会修改你的原始答案；如果原始答案文件的 SHA-256 指纹对不上，会直接拒绝重判。

0 分是不是说明我的 Agent 很差？

先分清两件事：0 分说明 16 道题一条条件都没过； PARTIAL / 待复核说明有题目根本没法判分，这时候连总分都不该看。

如果确实是 0 分，先看报告里逐条的理由 —— 很可能是格式问题（比如整段散文而不是 JSON）， 而不是「什么都不会」。这种情况下你应该先解决格式，再谈能力。

为什么报告里没有百分位、没有「超过 95% 的用户」？

因为没有可信的整体样本。要算百分位，需要一个中心化收集来的、覆盖真实用户的分数分布 —— 而这个工具根本不上传数据，所以公司手里没有这样一份数据。

任何声称「超过 X% 的用户」的本地工具，要么在偷偷上传，要么在编一个分布。 我们两个都不做。

关于运行与报错

提交时报「批次不包含这些题目」怎么办？

答案文件的键写错了批次。每一批只接受本批的 4 个题目 id， 具体是哪 4 个，看上一批输出里的 items[].id，或者 resume 一下。

按正确的 id 改好文件重交即可，这一批还没有被判分。

提交时报「已提交并判分，拒绝覆盖」怎么办？

这一批已经用另一份答案判过分了。这是设计上的保护： 不允许用新答案覆盖已判分的结果，否则「先看答案再改」就成立了。

两条路：继续下一批（接受这一批的结果），或者新开一局重来（start 拿新 runId）。 不要试图改 state.json 绕过 —— 那会让整份报告失去意义。

为什么某道题显示「待复核」？

说明这道题的答案有内容，但一个可用字段都没识别出来。 判分器宁可不下结论，也不把它当成「知识错误」扣 0 分。

处理：status --run <ID> 看是哪几题 → 改成规范的 JSON 格式 → 新开一局。 已判分的批次不能覆盖，所以没法原地修。

机制细节见NEEDS_REVIEW 什么时候触发。

中途上下文丢了 / 进程被杀了，之前的算白跑吗？

不算。状态全部落在磁盘上，每次提交都是原子写（临时文件 → fsync → rename）， 不会写一半坏掉。 

node scripts/cli.mjs status --run <RUN_ID>
node scripts/cli.mjs resume --run <RUN_ID>

resume 会直接给出下一批题目，接着跑就行。

装了半天，skill 目录里没有 lezi-bench 这一条？

最常见的原因是目录名不对。必须同时满足：

  • 目录名是 lezi-bench（带连字符），不是 lezibench；
  • 结构与 name 字段一致；
  • 只嵌一层：<root>/lezi-bench/SKILL.md，不能再往下一层。

满足不了这些条件的包会被静默跳过，只留一条 warning —— 模型端看不出「不存在」和「存在但非法」的区别。

关于可信度

题目和判分器都在源码里，那不就能作弊了？

能。改题、改判分器、改答案文件，都能拿到 100 分。我们不做任何防作弊机制， 也不宣称有。

这是一个明确的产品选择：既然做不到真正的防篡改（客户端天然可改）， 就不该用「防作弊」这种词给自己贴金。改出来的 100 分只对改的人有意义 —— 而这个工具的目标用户，是那些想知道真实水平的人。

那它凭什么可信？

可信度来自「可核对」，而不是来自「不可见」：

  • 每条扣分都对应一条带编号的条件，条件文本在源码里能查到；
  • 判分是确定性的，同一份答案重判结果相同；
  • 报告里印着 exam / grader 版本与题库指纹，改过就露馅；
  • 原始答案带 SHA-256 指纹，重判时比对，被改过就拒绝。

它不保证你诚实，只保证你没法在不被发现的情况下不诚实。

它会不会偷偷把分数上报？

不会，也不可能 —— 代码里没有网络调用。你可以自己搜一遍： 整个 src/ 和 scripts/ 里没有 fetch、 没有 http / https 模块引用、没有 websocket。

不用相信我们的承诺，直接读代码就行。

和虾跑分的区别

你们跟虾跑分（paofen.cocoloop.cn）是什么关系？

没有关系。我们是独立实现，题库、判分器、交互模型都是自己写的。 2026-10-29 我们对它做过一次匿名黑盒实测，目的是搞清楚「哪些设计值得学、哪些坑必须避开」， 不是为了做竞品分析报告。

实测记录：research/COMPETITOR_TRIAL.md。

最关键的差别是什么？

一句话：交付物的位置。

虾跑分把报告放在一个在线页面上，finish 返回 reportUrl。 实测于 2026-10-29，那个页面连试三次都打不开（502 / 超时 / 502）， 而同一域名下 /api/* 和首页都正常 —— 说明跑分算完了，但用户看不到结果。

LeziBench 的报告是本地文件，路径打印出来，双击就能看，断网也能看。 只要磁盘还在，报告就还在。

证据：COMPETITOR_TRIAL.md §5 P1。

还改掉了哪些具体问题？

三条有实测证据的：

  • 重复提交会静默跳题。实测于 2026-10-29：重复提交 q04 后，下一题直接变成 q06， q05 被永久跳过且无提示。LeziBench 用 payload 哈希做幂等，重复提交返回同一结果。
  • 文档与实现不一致。首页 FAQ 说「8 批 × 2 题」，但 API 全程逐题下发、无任何 batch 字段。 LeziBench 的批次是硬约束，写错批次直接报错。
  • 段位口径三处打架。8 级 / 6 档 / 93+ / 90+ 四种说法并存。 LeziBench 只有一套 LEVELS 常量，报告、网站、终端引用同一份。

证据：P4、 P2、 P3。

有没有什么是你们学它的？

有，而且不止一处：

  • 逐题给 details 的思路是对的，我们保留了，并且把它从「只有模型能看到」改成「直接写进报告给用户看」。
  • 统一的中文错误文案（{"error": string}）比一堆错误码友好，我们借鉴了形态（但 CLI 场景下用退出码区分类型）。
  • skill 驱动的交互模型本身成立且足够简单，这一点在实测里得到了验证。

我们明确不学的：用提示词强制 Agent「必须展示链接」的做法。
