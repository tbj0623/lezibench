评分方法论，以及十六道题的每一条条件

LeziBench 的判分器是一段确定性代码，不是一次模型调用。这一页解释它为什么这样设计， 然后把 16 道题、44 条评分条件原样列出来 —— 和源码里的 publicCriteria 逐字一致。

一局是怎么跑的

题库固定 16 题，分 4 批、每批 4 题。一次 start 只会把第 1 批的 4 道题交给你， 提交后才会拿到第 2 批。这个顺序由题库自检强制：assertCatalogIntegrity() 要求每批恰好 4 题， 不满足就不允许开考。

状态机是 created → awaiting_batch_N → … → completed。每次提交做四件事： 校验题目 id 属于本批 → 逐题判分 → 原子落盘（同目录临时文件 → fsync → rename）→ 返回下一批或最终结果。

提交是幂等的

每次提交会对「批次号 + 排序后的整批答案」算一个 SHA-256 payload 哈希。 哈希相同：返回 idempotent: true，不重复计分、不推进题目，你拿到的是同一个结果。 哈希不同：直接报错「该批已经提交并判分，拒绝用不同答案覆盖」。

这一条不是可选的健壮性优化。任何带自动重试的客户端，如果重复提交会静默跳题， 总分就会被无端压低而没有任何提示。同一批提交两次必须等价于提交一次。

缺答按 0 分，但整局不出「完整成绩」

允许某批少答几题（比如模型输出被截断），缺的题记为 MISSING_ANSWER、按 0 分处理， 理由会写进报告。但只要没答满 16 题，报告状态就降级为 PARTIAL， 不给段位、不给完整总分，避免拿一份残缺试卷的成绩去跟别人比。

为什么用原子条件打分

每道题由若干条「原子条件」（criterion）组成，每条有自己的 id、分值和一句可核对的条件文本。 判分器对每条条件独立返回 passed 与 reason，题目得分就是通过的条件分值之和。

这样做有三个直接后果：

  • 没有「差不多对」的模糊地带。「截止时间正确」和「附件要求正确」是两条独立条件（1 分 + 3 分）， 答对一个就是拿一条的分，不存在「整体印象给 2 分」。
  • 扣分可以被反驳。每条失败条件都带具体理由，比如 应付款应为 65，实际为 70。你可以打开源码对一遍，确认是判分器错了还是答案错了。
  • 分值能反映难度，而不用改口径。基础题通常 4 分、两条条件（1 + 3）； 挑战题 9 分、三条条件（3 + 3 + 3），且每条都要求「全部正确」才给分。

结构性自检

开考前会逐条校验，任何一条不成立就拒绝出题：

  • 恰好 16 题，ID 不重复；总分恰好 100。
  • 四个维度各恰好 25 分，每维的分值结构必须是 [4, 6, 6, 9]。
  • 每批恰好 4 题；难度分布恰好 4 基础 / 8 标准 / 4 挑战。
  • 每题的子条件分值之和必须等于该题满分，且每个子分都是正整数。
  • 0 到 100 之间每一个整数分都必须可达 —— 用子条件分值做可达性枚举，取不到的分直接判为命题缺陷。

最后一条容易被当成形式主义，其实很实用：如果某道题的子条件分值组合有缺口， 就会出现「无论怎么答都拿不到某个分数」的情况，分数分布会莫名其妙地跳过一段。 枚举一遍就能在命题阶段把这类问题挡住。

判分器结构校验

每道题的 grade() 返回的条件必须与题目的 publicCriteria 一一对应， 且分值完全相同。少一条、多一条、分值对不上，判分器立即抛错 —— 不会静默按错的口径给分。

为什么不用 LLM 当裁判

用另一个模型给答案打分，会引入四种难以消除的问题：同一份答案重判可能得分不同；评分口径随模型版本漂移； 判分过程本身不可审计；以及最要命的一条 —— 你不知道它是因为答案错了扣分，还是因为它看错了答案。

LeziBench 的选择是完全确定性的判分：

  • 同一份答案，任何时候重判都是同一个分数。 想验证的话：regrade --run <ID> 会从落盘的原始答案重新判一遍，改动只体现在 grader 版本升级时。
  • 重判不碰原答案。原始答案写入时带 SHA-256 指纹，重判前会比对指纹； 指纹对不上就拒绝重判（说明文件被外部改过）。旧轨迹归档到 evidence/。
  • 没有网络调用。判分器里没有任何 HTTP 客户端，也没有 API key 的概念。断网照样出分。

代价是：题目必须是「答案可以被形式化判定」的那一类。开放式写作、审美、长文论证这类任务， 这套判分器测不了，我们也不假装能测 —— 见局限。

等价答案怎么归一

判分只在格式层面做归一化，绝不做语义猜测。识别不出就返回空，让这道题进入待复核， 而不是猜一个「大概是想说 X」然后扣分。

文本

  • Unicode NFKC 归一（全角转半角）、折叠连续空白、去首尾引号与尾部标点。
  • 不删除否定词、不删除数字：「不需要预算表」里的「不」必须保留，否则语义就反了。
  • 中文直引号、直角引号、弯引号视为等价包裹符。

数字

  • 支持千分位（1,234）、货币符号（￥52元）、中文数字（五十二）。
  • 整数精确相等；小数按 1e-6 的相对容差比较，避免浮点误差误判。
  • 拒绝 NaN、Infinity、空串、以及「52 和 57」这种含多段数字的混杂串 —— 不猜你指哪个。

布尔

  • true / 是 / 需要 / 附上 视为真；false / 否 / 不需要 / 不附 视为假。
  • 先匹配更长的否定形式，防止「不需要」被「需要」抢先匹配成真。
  • 也许吧 这类含糊措辞解析为 null，不猜真假。

列表与集合

  • JSON 数组、逗号分隔、顿号分隔、编号列表，都能识别成同一个字符串数组。
  • 题目说「顺序不限」的用集合比较；说「按序排列」的用序列比较。两种比较是分开实现的，不会混用。
  • 商品编码大小写、空格不敏感（s1 与 S01 等价）。

同义表述

少数题目的答案字段带一张显式别名表，例如审批结论里「部分通过 / 按比例批准」等价于「部分批准」。 别名表写在题目源码里，可以逐条查；没有写进表的表述不会被当作等价。

JSON 抽取

  • 先找整段 JSON，再找 ```json 代码块，最后才做括号配平扫描。
  • 同时出现多个互相冲突的 JSON 片段时，判为不可解析 —— 绝不擅自挑一个当答案。
  • 字段名大小写、下划线、空格不敏感（budget_attached 与 budgetAttached 等价）。
  • 字段在对象不同层级出现且值不同时，标记为冲突而不是取第一个。

判分器不执行被测答案里的任何内容：没有 eval、没有 new Function、没有动态 import。 传进来的字符串一律当文本处理。

NEEDS_REVIEW 什么时候触发

这里有一个重要的设计取舍：「答错了」和「看不懂你在答什么」是两回事。 前者是能力问题，照常扣分；后者是解析故障，不能算成知识错误 —— 否则格式不对就会被误判成不会做。

判分结果有四种状态：

  • GRADED —— 正常判分。哪怕全错，也是这个状态，分数为 0，理由是「答案不对」。
  • MISSING_ANSWER —— 这道题没交任何内容。按事先公告的缺答 0 分处理。
  • UNPARSEABLE —— 有内容，但一个可用字段都识别不出来。标记待复核，不计为知识错误。
  • SCORER_ERROR —— 判分器内部异常。同样标记，等修复后 regrade 重判。

判定门槛很低也很明确：只要有任意一个字段被成功识别，就按正常路径判分（缺的字段对应的条件不通过）； 只有零个可用字段才进入待复核。这个界限保证「漏写字段」不会变成「系统故障」， 而「答非所问」不会被强行打成分数。

任何一道题处于待复核或评分器错误状态，整份报告的状态就是 PARTIAL： 不给段位、不给完整总分，报告里会列出是哪几题、什么原因。

换句话说：拿不到分和这份卷子下不了结论是两种不同的事。 前者照实扣分，后者拒绝下结论。

版本化：exam / grader / contract

三个版本号分别管三件不同的事，都写进每一局的 state.json 和每一份报告：

三个版本号的含义
字段变更含义当前值
examVersion 题目内容可能变化。跨版本继续运行会被拒绝，必须重新 start。 1.2.0
graderVersion 判分规则可能变化。可以用 regrade --grader <ver> 在新版本下重判旧答案。 1.2.0
contractVersion 评分合同的整体约定变化（字段语义、状态机、报告结构）。 1.0.0

题库指纹

每局还会记录一个 catalogFingerprint：由 16 道题的 id、维度、难度、分值、批次， 每条子条件的 id / 分值 / 文本，以及两个固定探针 seed 下的题面共同算出的 SHA-256。当前值以 doctor 输出为准（本仓库当前是 d44f1304968e…）。

指纹的作用是「发现题库被改过」：两份报告如果版本都相同、但指纹不同， 说明其中一份的题库被改过，两者的分数不可比。

但它不是「同一份卷子」的证明。指纹只采样 fp-probe-1 / fp-probe-2 两个探针 seed，所以它保证的是 「评分条件 + 这两个 seed 下的题面」一致，不保证所有 seed 的题面一致。 同一个指纹下的两次运行，实际题目可能完全不同 —— 这是概率性覆盖，不是完备校验。

另外，指纹算法本身升级过（早期版本不含题面探针）。不同算法版本算出的指纹数值不可直接比较， 这时只能靠版本号判断。

比较成绩的唯一合法条件

两次运行可比，需要同时满足三个条件：examVersion 相同、 graderVersion 相同、catalogFingerprint 相同。 少任何一个，都不是同一把尺子，横比没有意义。

逐题评分规则（16 题，44 条条件）

下面是每一道题的题号、维度、难度、满分，以及全部公开评分条件 —— id、分值、条件文本三样都与源码逐字一致。这些文本也是答题时 start 会打印给你的 「评分条件（公开）」，答题方和判分器看的是同一份。

注意：条件是判分口径，不是答案。题目实例的日期、金额、姓名等具体数据由 seed 随机生成， 每次开考都不同；条件文本描述的是「什么样的答案算对」，不泄露具体答案。
