给 Agent 的一份试卷，
判完分当场能查账。 16 题 · 100 分 · 4 个维度，全部在你自己的机器上跑完。

LeziBench 是一套公开题库的本地自测。判分不经过任何服务器，报告直接写成文件； 每一分为什么给、为什么扣，都能对应到源码里一条带编号的评分条件。

  • 16 题 4 批 × 4 题，一次答完一批再提交
  • 100 分 4 基础 + 8 标准 + 4 挑战
  • 4 维 × 25 每维固定 4 / 6 / 6 / 9 分
  • 0 次请求 判分与报告全程不发网络请求

100 分是怎么拆开的

四个维度各 25 分，维度之间不加权、不换算 —— 总分就是十六道题得分直接相加。 每个维度内部固定是「1 道 4 分 + 2 道 6 分 + 1 道 9 分」，所以任何一维都不可能靠一两道题刷满。

这些数字不是写在文案里的：assertCatalogIntegrity() 在每次开考之前逐条校验题目数、满分、维度合计、难度分布与子条件合计，任一条不成立就拒绝出题。

四个维度的题目与分值构成
维度 题号区间 基础 4 分 标准 6 分 × 2 挑战 9 分 合计
指令理解 INSTRUCTION I01–I04 I01 I02 · I03 I04 25
逻辑推理 REASONING R01–R04 R01 R02 · R03 R04 25
信息整理 DATA D01–D04 D01 D02 · D03 D04 25
状态追踪与纠错 CORRECTION C01–C04 C01 C02 · C03 C04 25
合计 16 题 4 题 8 题 4 题 100
为什么按批次交卷
一次只看 4 道题，做完一批提交再看下一批。避免十几道题一起摆出来时，把注意力从「读清条件」变成「扫一遍挑软柿子」。
为什么是 4 / 6 / 6 / 9
基础题只有一两个条件，挑战题的每一个分项都必须同时成立才给分。分值差直接体现「多条件同时正确」比「单点正确」难多少。
子条件是最小计分单位
没有「差不多对」的半分。每条子条件是独立的 1–3 分，判分器逐条返回通过与否和理由，总分等于通过的子条件分值之和。
0–100 每一分都可达
题目自检会枚举全部子条件分值的组合，确认 0 到 100 之间不存在取不到的整数分。存在取不到的分数就说明命题有结构性缺口，直接拒绝开考。

它跟「跑分网站」不一样在哪

下面三条不是口号，是三个可以在本机复现的机制。第一条尤其容易被忽略： 很多跑分产品把成绩放在一个在线页面上，那个页面一旦打不开，这次跑分就等于没发生。

报告是文件，不是链接

跑完就在本机生成一个自包含 HTML，双击打开，断网也能看。

src/report/html.mjs

报告不依赖任何在线服务、CDN、字体、统计脚本 —— 全部样式内联在同一个文件里。 有个直接的对照：实测于 2026-10-29，虾跑分的 finish 接口正常返回了 reportUrl，但同一个 URL 连试三次（502 / 超时 / 502）都打不开， 而同一域名下的 /api/* 与首页都是 200。
COMPETITOR_TRIAL.md §5 P1 · 证据 raw/report_page*.body.txt

每一分都能追到一条带编号的条件

扣分不是「感觉不太好」，是一条 id、一个分值、一句理由。

method.html · 逐题规则

报告里每条扣分都长这样：I01.C2 · 3 分 · 错误地表示仍要附预算表。 这条 I01.C2 在题库源码里有同名定义，条件和分值必须与判分器返回的一致，否则判分器直接抛错拒绝出分。 你不会看到「综合表现中等」这种没法核对的评语。
src/exam/items/instruction.mjs · publicCriteria

断网可用，答案不出本机

doctor、判分、出报告，全程零网络请求，零 npm 依赖。

privacy · 数据存在哪

整个仓库没有 node_modules 依赖，也没有任何 fetch / HTTP 客户端调用。 答案写到本机数据目录，报告也写到本机；没有任何「上传后返回评分」的路径， 因为评分这一步根本不离开你的机器。
FAQ · 它到底会不会联网

五档段位，一套阈值

段位只是把总分切成五段的标签，没有任何额外含义。阈值写在 manifest.mjs 的 LEVELS 里，报告、网站和终端输出引用的是同一份常量 —— 不存在「文案说一套、代码算一套」。

卓越 90 – 100
优秀 80 – 89
良好 65 – 79
基础 50 – 64
需要提升 0 – 49

区间是闭区间、且首尾相接：89 分是「优秀」，90 分才是「卓越」。含待复核题目的运行不给段位 —— 分数不完整的时候，档位也是不完整的。

和虾跑分比，我们改掉了什么

2026-10-29 我们对虾跑分（paofen.cocoloop.cn）做了一次匿名、隔离、限量的黑盒实测： 23 次 HTTP 请求，未登录、未上传任何数据、未复制对方题库。 下面每条都标了证据位置，没被证实的事我们一律不写。

这不构成对虾跑分整体产品质量的判断 —— 我们只记录自己在那个时间窗口里实际看到了什么。 对方是否另有未触发的机制，本报告不作推测。

状态推进是幂等的

同一批用完全相同的答案重复提交，返回同一个结果，不重复计分，也不推进题目。

实测于 2026-10-29：虾跑分在 q04 已提交后再提交一次 q04，服务端返回 200， nextQuestion 却直接跳到 q06 —— q05 被静默跳过， 客户端没有任何提示。任何带自动重试的集成方都会因此不明不白地丢分。
COMPETITOR_TRIAL.md §5 P4 · 证据 raw/err_dup_answer_q04.body.txt
LeziBench 的做法：提交时对整批答案算 payload 哈希。哈希相同 → 返回 idempotent: true， 分数不变；哈希不同 → 直接拒绝覆盖并报错。

文档写的批次结构 = 代码里的批次结构

说的是 4 批 × 4 题，那 start 返回的就是 4 道题，submit 收的就是这 4 道。

实测于 2026-10-29：虾跑分首页 FAQ 写「16 道测试项分 8 个批次进行，每批 2 题」， 但 API 自始至终一次只返回一道 nextQuestion，响应里没有任何 batch / group 字段。 「8 批 × 2 题」与实际接口对不上。
COMPETITOR_TRIAL.md §5 P2 · 证据 raw/homepage.body.txt 与 raw/start_*.body.json
LeziBench 的批次是硬约束：题库自检要求每批恰好 4 题，submit 校验题目 id 必须属于该批，写错批次直接报错。

不把「唯一交付物」放在一个会过期的页面上

报告落盘，路径打印给你，同时附一份纯文本摘要可以直接贴进对话。

实测于 2026-10-29：虾跑分的 finish 会返回 mustShowToUser 和 instruction 两个字段，用提示词的语气要求 Agent「必须把链接展示给用户」。 当唯一的报告页打不开时，这套设计就没有兜底方案了。
COMPETITOR_TRIAL.md §5 P6 / P7
LeziBench 不向 Agent 下达指令式文案。报告文件 + 终端摘要 + 可选的 JSON 证据，三条路径各自独立可用。

我们没有做的、也不打算做的

  • 不搞排行榜。没有中心服务器，就没有可以可信排名的共同基准；报告里会明确标「本地规则核验 · 非认证成绩」。
  • 不宣称防作弊。题库和判分器都是公开源码，任何人都能读、能改。改了就失去意义 —— 这是设计前提，不是漏洞。
  • 不宣称全平台兼容。目前只有 DSH 是真机验证过的。见支持环境表。
  • 不用 LLM 当裁判。判分是确定性代码，同一份答案任何时候重判都是同一个分数。

开一场，四条命令

在 SKILL.md 所在目录执行。doctor 不过就别往下走 —— 环境有问题时硬跑出来的分数不作数。

需要 Node.js ≥ 18.17。无需 npm install，仓库里没有运行时依赖。

  1. 自检

    # 5 项全过才会打印「全部通过，可以开考。」
node scripts/cli.mjs doctor

  2. 开始一局，拿到第 1 批 4 道题

    node scripts/cli.mjs start --mode standard --json

    输出里的 runId 后面每条命令都要用。

  3. 作答并提交，重复 4 次

    node scripts/cli.mjs submit --run <RUN_ID> --batch 1 --answers-file answers-batch1.json

    答案文件长这样，键是题目 id（本批的 4 个）：

    {
  "answers": {
    "I01": { "deadline": "周三上午10点", "budgetAttached": false },
    "I02": { "selected": ["S01", "S03"], "rejected": ["S02"] },
    "I03": { "rule": "R3", "decision": "批准", "escalate": false },
    "I04": { "status": "已通过", "owner": "小周", "deadline": "周三" }
  }
}

    上面只是格式示意，别照抄 —— 每局题目由 seed 生成，实际条件以 start 输出的题面为准。

  4. 出报告

    node scripts/cli.mjs report --run <RUN_ID> --format html
node scripts/cli.mjs report --run <RUN_ID> --format summary

    HTML 是自包含文件，命令会打印绝对路径；summary 是纯文本，可以直接贴进对话。

这份成绩是什么，不是什么

LeziBench 是本地、公开题库、可审计的自测。它测量的是「按这套公开规则，这次做得怎么样」， 不是「这个模型客观上有多聪明」。请把它当成体检报告，不是学位证书。

  • 不是认证。没有任何第三方见证、没有防篡改、没有身份核验。报告自己就印着「非认证成绩」。
  • 不防作弊。题目、评分条件、判分器全在源码里。改题改分当然能拿高分，但那份分数只对你自己有意义。
  • 跨版本不可比。只有 examVersion 与 graderVersion 都相同的两次运行才能拿来比。报告里两个版本号都印着。
  • 16 题覆盖面有限。它测不出长上下文、多轮工具调用、代码工程能力、审美、事实准确性。具体缺口见 局限。
  • 耗时不是能力指标。单次运行的秒数受宿主机、模型负载、网络往返影响，只作参考。

跑一场，看看它到底哪里会掉链子。

四批、十六题，大概十分钟。报告会告诉你具体是哪一条条件没过，而不是一个让人安心的整数。
