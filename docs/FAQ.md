# FAQ — 常见问题

> 按「最容易被误解的排前面」排序。每个回答尽量指到具体代码或实测记录，而不是给一句听着舒服的结论。
>
> 更多边界见 [LIMITATIONS.md](LIMITATIONS.md)；逐题规则见 [SCORING.md](SCORING.md)。

---

## 一、它到底会不会联网

### Q1. 跑分过程需要联网吗？

**不需要。** 判分、写状态、生成报告全部走本地文件系统。代码里没有任何 HTTP 客户端，
也没有 API key 的概念 —— 不是「默认不联网」，是**根本没有联网的代码路径**。

验证方法：断网后跑 `node scripts/cli.mjs doctor`，五项仍然全 ✔；再跑完整一局，报告照样生成。

见 [PRIVACY.md](PRIVACY.md)。

### Q2. 我的答案会被上传到哪里吗？

**不会。** 答案写到本机数据目录下的 `runs/<runId>/answers/`，报告写在同目录的 `reports/`。
除此之外没有第二个副本。

### Q3. 为什么不需要 API key？

因为判分不调用任何模型。判分器是一段确定性 JavaScript 代码，对照题目的 `publicCriteria`
逐条判定。没有模型参与，自然不需要凭据。

这也是它能在断网环境里出分的原因。设计理由见 [METHODOLOGY.md §3](METHODOLOGY.md#3-为什么不用-llm-当裁判)。

### Q4. 网站本身有追踪吗？

没有。纯静态页面：没有 Cookie、没有分析脚本、没有外部字体、没有 CDN。
唯一的浏览器存储是一个 `localStorage` 键，用来记住你选的明暗主题。

## 二、它测的到底是什么

### Q5. 它测的是「聪明程度」吗？

不是。它测的是「在给定材料、给定规则、要求输出结构化答案」这一类任务上，
这一次做得怎么样。四个维度：

| 维度 | 覆盖内容 |
|---|---|
| **指令理解** | 多条通知里哪条最终有效、规则有例外时怎么处理 |
| **逻辑推理** | 算账、排顺序、满足多约束的最优解、排除法求解 |
| **信息整理** | 去重排序、区分事实与推断、两表合并且找冲突、按规则分类 |
| **状态追踪与纠错** | 改来改去之后的最新状态、发现算式错误、新旧规则更迭、定位 bug 根因 |

完整的边界见 [LIMITATIONS.md §3](LIMITATIONS.md#3-16-题覆盖不到的东西)。

### Q6. 为什么只有 16 题？会不会太少？

16 题确实不多，这是一个明确的权衡：题少才能保证每一题都被认真设计成「有区分度」，
且每一条评分条件都能被人工复核。

但也正因为题少，单次运行的方差不可忽略。**要看水平就多跑几局看分布**，而不是盯一次分数。

### Q7. 为什么分 4 批，不能一次把 16 题都给我吗？

可以，但当前版本不提供。分批是刻意的：一次只看 4 道题，注意力会集中在「把条件读清楚」，
而不是「扫一遍挑容易的做」。

另外，分批让「提交幂等」「断点续跑」这两件事变得简单可靠：每一批是一个原子单元。

### Q8. 题目每次都不一样吗？

题目的**结构**固定（16 道、4 批、分值不变），但**数据**由 seed 生成：
日期、金额、人名、商品编号、名单都不同。同一道题连跑两次，题面是不一样的。

传 `--seed <值>` 可以复现同一套题面 —— 排查问题或者对比时有用。

## 三、关于分数与比较

### Q9. 80 分算好吗？

段位表：90+ 卓越 / 80–89 优秀 / 65–79 良好 / 50–64 基础 / 0–49 需要提升。所以 80 分落在「优秀」。

但比段位更有用的是看**哪几条条件没过**。一个 80 分里有 20 分是怎么丢的，
比「80 分算不算好」这个问题重要得多。

### Q10. 我能拿这个分数跟别人的比吗？

只有在下面条件**全部满足**时才有意义：

- 两次运行的 `catalogFingerprint` **相同**（这是最硬的一条，见下题）；
- 采样参数（temperature 等）相同；
- 工具配置与系统提示相同；
- 各自跑了多局，比的是分布而不是单次结果。

少任何一条，这个比较就不成立。

### Q11. 为什么不能只看 `examVersion` / `graderVersion`？

因为版本号是**人手动升的**，可能漏升。而 `catalogFingerprint` 是对题库内容算的 SHA-256，
覆盖两样东西：

- 全部 16 题的评分条件（id / 分值 / 文本）；
- 16 题在固定探针 seed 下生成的题面。

**内容一变，指纹就变。**

我们自己的实测里就真遇到过：某一批运行的 `examVersion` 与 `graderVersion` **全都是 `1.0.0`**，
但题库与评分条件实际改过，指纹随之变化 —— 只看版本号会误以为它们可比。

**但指纹也有边界：** 题面探针只用几个固定 seed。指纹相同只保证「那几个探针 seed 下的题面 +
全部评分条件」相同，**不能**保证所有 seed 的题面都逐字相同。某个随机分支没被探针触发时，
改题面可能不改变指纹。这是概率性覆盖。

**还有一层：** 如果两个指纹是不同算法版本算出来的（算法升级过），数值本身不可直接比较，
这时只能靠版本号判断。

所以判断两份成绩能不能比，**先比版本号，再比报告里印的题库指纹**。

### Q12. 为什么同一份答案重判，分数可能变？

正常情况下不会变 —— 判分是确定性的。分数变化只有一种合法来源：**grader 版本升级了**，判分口径变了。

`regrade` 会把重判前后的分数差异逐题列出来，并把旧轨迹归档到 `evidence/`。
它不会修改你的原始答案；如果原始答案文件的 SHA-256 指纹对不上，会直接拒绝重判。

### Q13. 0 分是不是说明我的 Agent 很差？

先分清两件事：

- **0 分**说明 16 道题一条条件都没过；
- **PARTIAL / 待复核**说明有题目根本没法判分，这时候连总分都不该看。

如果确实是 0 分，先看报告里逐条的理由 —— 很可能是格式问题（比如整段散文而不是 JSON），
而不是「什么都不会」。这种情况下你应该先解决格式，再谈能力。

### Q14. 为什么报告里没有百分位、没有「超过 95% 的用户」？

因为没有可信的整体样本。要算百分位，需要一个中心化收集来的、覆盖真实用户的分数分布 ——
而这个工具**根本不上传数据**，所以作者手里没有这样一份数据。

任何声称「超过 X% 的用户」的本地工具，要么在偷偷上传，要么在编一个分布。我们两个都不做。

## 四、关于运行与报错

### Q15. 提交时报「批次不包含这些题目」怎么办？

答案文件的键写错了批次。每一批只接受本批的 4 个题目 id。

看上一批输出里的 `items[].id`，或者跑 `resume --run <ID>` 它会直接给出下一批题目。
按正确的 id 改好文件重交即可，这一批还没有被判分。

### Q16. 提交时报「已提交并判分，拒绝覆盖」怎么办？

这一批已经用**另一份答案**判过分了。这是设计上的保护：
不允许用新答案覆盖已判分的结果，否则「先看答案再改」就成立了。

两条路：继续下一批（接受这一批的结果），或者新开一局重来（`start` 拿新 runId）。
不要试图改 `state.json` 绕过 —— 那会让整份报告失去意义。

### Q17. 为什么某道题显示「待复核」？

说明这道题的答案**有内容，但一个可用字段都没识别出来**。
判分器宁可不下结论，也不把它当成「知识错误」扣 0 分。

处理：`status --run <ID>` 看是哪几题 → 改成规范的 JSON 格式 → 新开一局。
已判分的批次不能覆盖，所以没法原地修。

机制细节见 [METHODOLOGY.md §5](METHODOLOGY.md#5-needs_review-什么时候触发)。

### Q18. 中途上下文丢了 / 进程被杀了，之前的算白跑吗？

不算。状态全部落在磁盘上，每次提交都是原子写（临时文件 → fsync → rename），不会写一半坏掉。

```bash
node scripts/cli.mjs status --run <RUN_ID>
node scripts/cli.mjs resume --run <RUN_ID>
```

`resume` 会直接给出下一批题目，接着跑就行。

### Q19. 装了半天，skill 目录里没有 `lezi-bench` 这一条？

最常见的原因是目录名不对。必须同时满足：

- 目录名是 **`lezi-bench`**（带连字符），不是 `lezibench`；
- 结构与 frontmatter 的 `name` 字段一致；
- 只嵌一层：`<root>/lezi-bench/SKILL.md`，不能再往下一层。

满足不了这些条件的包会被**静默跳过**，只留一条 warning ——
模型端看不出「不存在」和「存在但非法」的区别。

见 [INSTALL.md](INSTALL.md)。

## 五、关于可信度

### Q20. 题目和判分器都在源码里，那不就能作弊了？

能。改题、改判分器、改答案文件，都能拿到 100 分。我们**不做**任何防作弊机制，也不宣称有。

这是一个明确的产品选择：既然做不到真正的防篡改（客户端天然可改），
就不该用「防作弊」这种词给自己贴金。改出来的 100 分只对改的人有意义 ——
而这个工具的目标用户，是那些想知道真实水平的人。

### Q21. 那它凭什么可信？

可信度来自「可核对」，而不是来自「不可见」：

- 每条扣分都对应一条带编号的条件，条件文本在源码里能查到；
- 判分是确定性的，同一份答案重判结果相同；
- 报告里印着 exam / grader 版本与题库指纹，改过就露馅；
- 原始答案带 SHA-256 指纹，重判时比对，被改过就拒绝。

它不保证你诚实，只保证你没法在不被发现的情况下不诚实。

### Q22. 它会不会偷偷把分数上报？

不会，也不可能 —— 代码里没有网络调用。你可以自己搜一遍：

```bash
grep -rnE "fetch\(|node:(http|https|net|dgram)" src/ scripts/
```

应当没有任何输出。不用相信我们的承诺，直接读代码就行。

### Q23. 为什么报告里要标「非认证成绩」？

因为它是。没有第三方见证、没有身份核验、没有被测对象锁定、没有排行榜。
把这句话印在每份报告上，是为了防止一份自测成绩被当成认证去用。

## 六、关于和其他工具的区别

### Q24. 你们跟虾跑分（paofen.cocoloop.cn）是什么关系？

没有关系。独立实现，题库、判分器、交互模型都是自己写的。

2026-10-29 我们对它做过一次匿名、隔离、限量的黑盒实测（23 次 HTTP 请求，未登录、未上传任何数据、
未复制对方题库），目的是搞清楚「哪些设计值得学、哪些坑必须避开」。
完整记录见 [`research/COMPETITOR_TRIAL.md`](../research/COMPETITOR_TRIAL.md)。

### Q25. 最关键的差别是什么？

一句话：**交付物的位置**。

虾跑分把报告放在一个在线页面上，`finish` 返回 `reportUrl`。
**实测于 2026-10-29**，那个页面连试三次都打不开（502 / 超时 / 502），
而同一域名下 `/api/*` 和首页都正常 —— 说明跑分算完了，但用户看不到结果。

LeziBench 的报告是本地文件，路径打印出来，双击就能看，断网也能看。只要磁盘还在，报告就还在。

证据：[`COMPETITOR_TRIAL.md` §5 P1](../research/COMPETITOR_TRIAL.md#p1--报告页-502跑分能算完但用户打不开报告-最高优先级)。

### Q26. 还改掉了哪些具体问题？

三条有实测证据的（全部实测于 2026-10-29）：

| 问题 | 我们的做法 |
|---|---|
| **重复提交会静默跳题。** 重复提交 q04 后，下一题直接变成 q06，q05 被永久跳过且无提示 | 用 payload 哈希做幂等，重复提交返回同一结果，不推进题目 |
| **文档与实现不一致。** 首页 FAQ 说「8 批 × 2 题」，但 API 全程逐题下发、无任何 batch 字段 | 批次是硬约束，题库自检要求每批恰好 4 题，写错批次直接报错 |
| **段位口径三处打架。** 8 级 / 6 档 / 93+ / 90+ 四种说法并存 | 只有一套 `LEVELS` 常量，报告、网站、终端引用同一份 |

证据：同上文件 §5 P4 / P2 / P3。

### Q27. 有没有什么是你们学它的？

有，而且不止一处：

- **逐题给 `details` 的思路**是对的，我们保留了，并且把它从「只有模型能看到」改成「直接写进报告给用户看」；
- **统一的中文错误文案**（`{"error": string}`）比一堆错误码友好，我们借鉴了形态；
- **skill 驱动的交互模型**本身成立且足够简单，这一点在实测里得到了验证。

我们明确**不学**的：用提示词强制 Agent「必须展示链接」的做法。

## 七、关于贡献

### Q28. 我能加题吗？

可以，但门槛不低。必须同时提交：

- 题目实现（`generate` / `oracle` / `grade`）；
- **≥5 个正例、≥5 个反例**（证明判分器真的能区分）；
- 通过全部结构自检。

详见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

### Q29. 我能改评分条件吗？

能改，但改条件文本 = 改判分口径，必须同时升 `graderVersion`，并在 CHANGELOG 里说明旧成绩不可比。

**不允许**为了让某个模型的分数变好看而调整条件或分值 —— 这类 PR 会被拒绝。

### Q30. 发现判分器有 bug 怎么办？

见 [SECURITY.md](../SECURITY.md)。简单说：如果在公开仓库提 issue，
只描述「什么样的输入得到了什么结果」，**不要贴出完整标准答案**（那会破坏其他人后续跑分的公平性）。
