# METHODOLOGY — 评分方法论

> 面向：想知道「这套分数凭什么算数」的人，以及要改题目/判分器的贡献者。
> 配套：逐题规则见 [SCORING.md](SCORING.md)；边界见 [LIMITATIONS.md](LIMITATIONS.md)。
> 版本：以 `node scripts/cli.mjs version` 的输出为准（本文不硬编码版本号，避免与代码脱节）

---

## 0. 一句话

LeziBench 把「一次能力测评」拆成**十六道题 × 若干条原子条件**，
用一个**确定性的本地判分器**逐条核验，产出**可以逐分追溯**的成绩单。

三个设计选择撑起了这句话，下面逐个解释为什么：

1. 为什么是这 4 个维度；
2. 为什么用原子条件而不是整体打分；
3. 为什么**不**用 LLM 当裁判。

---

## 1. 为什么是这 4 个维度

### 1.1 选维度的判据

一个维度要进这份试卷，必须同时满足三条：

| 判据 | 含义 | 反例（因此被排除） |
|---|---|---|
| **可形式化** | 正确答案能被代码判定对错，不需要人来品味 | 文笔好坏、方案优雅度、审美 |
| **可原子化** | 能拆成若干条互不重叠的子条件 | 「整体回答质量」 |
| **可区分** | 不同能力的被测对象会拿到不同的分，而不是全员满分或全員零分 | 「1+1=?」 |

这三条把候选维度压得很窄。最终留下 4 个，每个 25 分：

### 1.2 四个维度分别卡什么

**指令理解（instruction）**
真实任务里最常出错的地方不是「不会做」，而是「做错了那一版要求」。
多条通知先后发出、后面覆盖前面、中间夹一句「这次不用交了」、规则里带例外 ——
这一类**约束管理与优先级**能力，是 16 题里权重最高的隐性考点。

题目形态：4 条通知里找最终有效的那条；白名单 + 例外 + 状态过滤；编号优先级命中即停；四步指令更新后的一致状态。

**逻辑推理（reasoning）**
算账、排依赖、多约束下求最优、从线索里做排除。这四类覆盖了「结构化推理」的常见骨架，
且每一类都能精确判定：数值对不对、顺序合不合法、方案是不是真的最省、排列是不是唯一解。

题目形态：小票合计 + 满减；五步任务的合法拓扑序；三种餐盒的最低成本；六线索排除推理。

**信息整理（data）**
给的是一堆原始材料，要求整理成干净的结构：去重、排序、区分「事实 / 推断 / 信息不足」、
两张表合并且找出冲突、按一串规则给每个人分类。

这一类特别能暴露一个问题：**模型会不会把「没给的信息」当成「给了」**。
D02 就是专门测这个的 —— 甲项目的最终支出是空的，正确回答是「信息不足」，而不是拿预算去比。

**状态追踪与纠错（correction）**
最贴近真实工作的一类：状态被改过很多次之后现在是什么、算式哪里错了、新旧规则按哪个版本算、
脚本算错了根因在哪。

它的共同点是**必须在多步之间维持一致的世界状态**。这类能力在短对话里看起来没问题，
一旦步骤变多就开始漏。C02 的「撤回第 2 步」就是最小化的测试：撤回一笔出库，库存应该变多，不是不变。

### 1.3 为什么是 4 × 25，而不是加权

如果维度之间加权，就必须回答「为什么指令理解值 30 分而信息整理值 20 分」。这个问题的任何答案
都是产品判断，不是测量结论，而且会引入一个无法被审计的魔数。

等权 4 × 25 的好处是：**总分 = 四维之和，没有任何隐藏系数**。
你看到 74 分，就知道是 22 + 16 + 19 + 17。少了任何一层换算，就少了一处可以藏私的地方。

代价是它不表达「哪个维度更重要」。我们接受这个代价 —— 重要性取决于你的用途，
应该由读报告的人自己判断，而不是由题库作者预先加权。

### 1.4 每个维度为什么是 4 / 6 / 6 / 9

同一维度内，一道基础题（4 分，1–2 条条件）、两道标准题（各 6 分，3 条条件）、
一道挑战题（9 分，3 条 3 分条件且每条都要求全对）。

这个结构的作用是**让维度内部也有梯度**：只会做基础题的人拿 4 分，能做标准题但挑战题崩的人拿 16 分，
四道全对才是 25。如果四道题都是 6 分，就无法区分「稳但浅」和「能啃硬的」。

`assertCatalogIntegrity()` 会强制检查每个维度的分值恰好是 `[4, 6, 6, 9]`，
防止后续加题时无意中破坏这个梯度。

## 2. 为什么用原子条件打分

### 2.1 什么叫「原子」

一条原子条件 = **一个能独立判定真假的最小命题 + 一个确定的分值 + 一句可核对的条件文本**。

以 I01 为例（满分 4 分，2 条条件）：

| 条件 | 分 | 条件文本 |
|---|---:|---|
| `I01.C1` | 1 | 截止时间落在最终通知给出的日期与时段 |
| `I01.C2` | 3 | 明确表示不附预算表（budgetAttached=false） |

「截止时间对但附件要求错」= 1 分。「截止时间错但附件对」= 3 分。两个都错 = 0。两个都对 = 4。
没有「大概对了一半给 2 分」这种路径。

### 2.2 三条不变式

判分器（`src/grading/grade.mjs`）在每次判分时强制保证：

1. **只依据 `publicCriteria` 给分。** 不做任何跨题惩罚 —— 前一题错了不会影响后一题。
2. **check 必须与 criteria 一一对应，分值必须一致。** 少一条、多一条、分值对不上，直接抛错，
   不会静默按错的口径给分。
3. **每条 check 必须带 reason。** 哪怕是内部异常，也要写清楚是哪条条件、为什么没过。

### 2.3 这样做换来了什么

| 收益 | 具体表现 |
|---|---|
| **可反驳** | 你觉得判错了，可以打开 `src/exam/items/*.mjs` 对一遍条件文本，再看报告里的 reason，定位到具体哪一条。 |
| **可复现** | 同一份答案重判，结果完全一致。`regrade --run` 会把前后差异逐题列出；没有差异就一条都不列。 |
| **可分布** | 分数不是黑箱输出，而是一组布尔值的加权和。你可以统计「哪几条条件最常失败」，这比总分更有信息量。 |
| **可审计** | 题库自检会验证「0–100 每个整数分都可达」。如果命题有结构性缺口，分数分布会莫名跳过一段。 |

### 2.4 代价

原子条件要求每道题都能被形式化。这直接导致了一些任务进不了题库（开放式写作、审美、长文论证）。
这是**有意的收窄**，不是遗漏 —— 详见 [LIMITATIONS.md](LIMITATIONS.md)。

## 3. 为什么不用 LLM 当裁判

### 3.1 用模型打分会有四个问题

1. **不可复现。** 同一份答案，今天判 8 分，明天判 7 分。你无法区分「答案变了」和「裁判变了」。
2. **口径漂移。** 裁判模型升级一次，全部历史成绩作废，而你可能根本没意识到。
3. **不可审计。** 你拿到一个分数，但拿不到「为什么是这个分数」。追问得到的解释是**事后编的**，
   不是判分时真实使用的依据。
4. **判分与解题同源。** 如果裁判和被测是同一类模型，它会系统性偏好「像自己那样写」的答案，
   而不是「正确」的答案。这是一种无法通过换 prompt 消除的偏置。

### 3.2 LeziBench 的做法

判分是**纯函数**：输入（解析后的答案, 题目 facts）→ 输出（每条条件的 passed + reason）。
没有网络调用，没有随机数，没有模型。

具体保证：

- `src/grading/parse.mjs` 与 `src/exam/**` 里**没有任何** `fetch` / `http` / `https` 调用。
- 判分器不执行被测答案里的任何内容：没有 `eval`、没有 `new Function`、没有动态 `import`。
  传进来的字符串一律当文本处理（`tests/parse.test.mjs` 有专门的用例守着这条）。
- 重判时从落盘的原始答案重算，并先比对 SHA-256 指纹；指纹对不上就拒绝重判，
  防止「改完原答案再重判」。

### 3.3 那「理由」是谁写的

条件文本是**出题时静态写死的**（`publicCriteria[].text`），reason 是**判分时由代码拼出来的**
（例如 `应付款应为 65，实际为 70`）。两者都不是模型生成的。

这就是为什么报告里的每条理由都能直接对应到一行代码 —— 它不是「解释」，是**判定结果本身**。

## 4. 等价答案怎么归一

原则一句话：**只做格式层面的归一，绝不做语义猜测。识别不出就返回空，交给待复核。**

### 4.1 文本

- Unicode NFKC 归一（全角 → 半角）、折叠连续空白、去首尾引号与尾部标点。
- **不删除否定词、不删除数字。** 「不需要预算表」里的「不」必须保留，否则语义反转。
- 各种引号（`"` `'` `「」` `『』` `""` `''`）在包裹位置视为等价。

### 4.2 数值

- 支持千分位（`1,234`）、货币符号（`￥52元`）、中文数字（`五十二`）、分数（`3/4`）。
- 整数精确相等；小数按 `1e-6` 相对容差比较（避免浮点误差误判 `0.1+0.2`）。
- **拒绝**：`NaN`、`Infinity`、空串、含多段数字的混杂串（`"52 和 57"`）—— 不猜你指哪个。

### 4.3 布尔

- 真：`true / 是 / 需要 / 附上 / 包含 / 正确`
- 假：`false / 否 / 不需要 / 不附 / 不含 / 无误`
- **先匹配更长的否定形式**，防止「不需要」被「需要」抢先匹配成真。
- `也许吧` 这类含糊措辞 → `null`，不猜。

### 4.4 列表与集合

- 能识别 JSON 数组、逗号分隔、顿号分隔、编号列表（`1. a\n2. b`）。
- **集合比较**（顺序无关）与**序列比较**（顺序敏感）是两个独立函数，由题目按自己的语义选择，
  不会混用：
  - 「两组内部顺序不限」→ `sameSet`
  - 「按摊位序号升序排列」→ 逐位比较

### 4.5 同义表述

少数题目的答案字段带一张**显式别名表**，写在题目源码里，可以逐条查。
例如 I03 的审批结论：

```js
{ 批准: ['可以批准', '通过', '同意'],
  部分批准: ['部分通过', '按比例批准', '部分同意'],
  转人工: ['转人工复核', '人工复核', '需要人工'] }
```

**没写进别名表的说法不会被当作等价。** 这是「不猜」原则的直接体现。

### 4.6 JSON 抽取顺序

1. 整段是否是合法 JSON；
2. 是否是 ```json 代码块；
3. 最后才做括号配平扫描（只在前面都失败时兜底，避免把散文里的花括号当 JSON）。

多个互相冲突的 JSON 片段 → 判为不可解析，**绝不擅自挑一个**。
同名字段出现在不同层级且值不同 → 标记冲突，不取第一个。

### 4.7 字段名

大小写、下划线、空格、点号不敏感：`budget_attached` = `budgetAttached` = `Budget Attached`。

## 5. NEEDS_REVIEW 什么时候触发

### 5.1 核心区分

> **「答错了」和「看不懂你在答什么」是两回事。**

前者是能力问题，照常扣分；后者是解析故障，不能算成知识错误 ——
否则格式不规范就会被误判成「不会做」，这对被测对象不公平。

### 5.2 四种判分状态

| 状态 | 触发条件 | 计分 | 对整局的影响 |
|---|---|---|---|
| `GRADED` | 至少有一个字段被成功识别 | 按条件给分（可以是 0） | 正常 |
| `MISSING_ANSWER` | 这道题没交任何内容 | 0 分 | 报告标缺答 |
| `UNPARSEABLE` | 有内容，但**零个**可用字段 | 该题 0 分 | 整局降级 `PARTIAL` |
| `SCORER_ERROR` | 判分器内部异常 | 该题 0 分 | 整局降级 `PARTIAL` |

### 5.3 为什么门槛定在「零个可用字段」

`src/grading/grade.mjs` 的实际判断是：

```js
const usableFields = Object.keys(parsed.fields || {}).length;
if (usableFields === 0) → UNPARSEABLE
```

也就是说：**只要识别出哪怕一个字段，就按正常路径判分**（缺的字段 → 对应条件不通过）。
只有「一个都识别不出」才认为这是解析故障，而不是能力问题。

这个界限的效果是：

- 漏写一个字段 → 正常扣分（能力/细心问题，该扣）。
- 整段答非所问、格式完全不对 → 待复核（无法下结论，不硬扣）。

### 5.4 整局降级

`summarize()` 的逻辑：只要有一道题是 `UNPARSEABLE` / `SCORER_ERROR` / `SYSTEM_ERROR`，
整份报告状态就是 `PARTIAL`：

- 给「已判得分」但不给完整总分；
- **不给段位**（`level = null`）；
- 报告里列出是哪几题、什么原因。

同理，没答满 16 题也会降级为 `PARTIAL`，即使每道答了的题都是满分。

## 6. 版本化

### 6.1 三个版本号，三种含义

| 字段 | 变更含义 | 后果 |
|---|---|---|
| `examVersion` | 题目内容可能变化 | **跨版本不能继续运行**，必须重新 `start` |
| `graderVersion` | 判分规则可能变化 | 可用 `regrade --grader <ver>` 在新版本下重判旧答案 |
| `contractVersion` | 评分合同整体约定变化 | 报告结构/字段语义可能不同 |

三者都写进 `state.json`，也印在每一份报告上。

### 6.2 题库指纹：比版本号更细的那把尺

`catalogFingerprint` 是对下面这部分内容算的 SHA-256：

```
每个题的 { id, dimension, difficulty, points, batch,
          criteria: [{ id, points, text }, …],
          probes: [ probesSeed 下生成的 { prompt, criteria } , … ] }
```

也就是说，它由两部分共同决定：

- **`criteria`** —— 全部 16 题的评分条件 id / 分值 / 文本；
- **`prompts`** —— 16 题在若干**固定探针 seed**（`fp-probe-1`、`fp-probe-2`）下生成的题面。

**任何一条评分条件的文字变化、或探针 seed 下题面的任何变化，都会改变指纹。**

> ⚠️ **一个必须说清的覆盖边界：** 探针只有两个固定 seed，
> 所以「指纹相同」只保证「这两个探针 seed 下的题面 + 全部评分条件」相同，
> **不等于**「所有 seed 生成的题面都逐字相同」。
> 如果某道题的随机分支恰好没被那两个探针触发，改题面也可能不改变指纹。
> 这是**概率性覆盖**，不是形式化保证 —— 加探针可以提高覆盖率，但永远达不到「证明所有 seed 等价」。
>
> 想要真正完备，得对题面做形式化建模；那已经超出「一个指纹」能承担的职责。
> 指纹的定位是**发现大多数改动**，不是证明没改动。

为什么需要它：版本号是**人手动升的**，可能漏升；指纹是**内容算出来的**，不会漏。

我们在自己的实测里就真遇到过「版本号没动、题库动了」的情形：
早期的五轮真实运行中，`examVersion` 和 `graderVersion` 全是 `1.0.0`，
但题库与评分条件实际改过两次，指纹也随之变化。

**只看版本号会误以为那几轮可比。**

> 历史记录里的指纹值（如 `1b665890f294…` / `255c5caa2848…` / `5079d6dd5c99…`）
> 是在**旧版指纹算法**下算出来的快照。算法本身后来升级过（加进了题面探针），
> 因此**跨算法比较指纹数值没有意义** —— 那时只能用版本号判断，现在两者都要看。

### 6.3 比较成绩的合法条件

> **两次运行可比，需要同时满足：`examVersion` 相同、`graderVersion` 相同、`catalogFingerprint` 相同。**

| 情况 | 可比吗 | 原因 |
|---|---|---|
| 版本号相同、指纹相同 | ✅ | 同源，可以比。想比稳定性就在同源下重复跑多次看分布 |
| 版本号相同、指纹不同 | ❌ | 题库或评分条件被改过 |
| 版本号不同 | ❌ | 无论指纹是否相同都不可比（算法/口径可能都变了） |
| 指纹是不同算法版本下算的 | ❌ | 数值本身不可直接比较，只能靠版本号判断 |

## 7. 幂等与完整性

### 7.1 提交幂等

每次提交对「批次号 + 排序后的整批答案」算 SHA-256 payload 哈希：

- 哈希相同 → 返回 `idempotent: true`，**不重复计分，不推进题目**，返回同一个结果；
- 哈希不同且该批已判分 → **直接拒绝覆盖**。

为什么必须有：任何带自动重试的客户端，如果重复提交会静默跳题，总分就会被无端压低而没有任何提示。
一次提交和两次相同提交必须等价。

### 7.2 完整性

- 允许缺答（缺的题记 `MISSING_ANSWER`、0 分），但没答满 16 题时整局不构成完整成绩、不给段位。
- 已判分的批次不可用不同答案覆盖 —— 否则「先看结果再改答案」就成立了。
- 不能用其他批次的题目 id 提交，写错批次直接报错。

### 7.3 重判

`regrade` 从落盘的**原始答案**重新判分：

- 不修改原始答案；
- 重判前比对答案文件的 SHA-256 指纹，对不上就拒绝（说明被外部改过）；
- 旧判分轨迹归档到 `evidence/regrade-<ts>/before.json`；
- 前后分数差异逐题列出。

## 8. 判分器不做什么

明确列出来，避免误读：

- **不做跨题惩罚。** 前一题错了不影响后一题。
- **不判断「思路是否优雅」。** 只判结果对不对、关键字段有没有。
- **不给部分分之外的加权。** 每条条件的分值是固定的，不会因为「这题难」而放大。
- **不做语义推断。** 你说「周三吧大概」，如果解析不出标准字段就是解析不出，不猜。
- **不执行任何被测内容。** 没有 eval、没有动态导入。
